# Phase 1 Data Model: ORB Release 1

## Global conventions

UUIDv7 primary keys; immutable scoped references; UTC timestamps; `numeric` for quantity/weight/money/rates; ISO currency; integer aggregate `version`; actor/time on create/update. Approved versions, evidence, approval decisions, send manifests, and audit events are append-only. Business records cancel/reverse/supersede rather than delete. Unlike currencies are never summed. All cross-row totals and state changes use locked/serializable transactions.

## Access and masters

- `User(id, auth_subject, name_ar, name_en, locale, status, mfa_state)`.
- fixed `UserRole(user_id, role OWNER_ADMIN|OPERATIONS|FINANCE_VIEWER)`; a user may have several roles.
- `Party(id, reference, legal_name_ar/en, country_code, customer, supplier, sensitive_identity_ciphertext, status, version)`.
- `CoffeeSpecification(id, reference, origin, type, grade, crop_year, bag_type, standard_bag_weight, attributes, version)`.
- `Currency(code, decimals, active)` and `ExpenseCategory(code, name_ar/en, active)`.

Server-side projections hide supplier cost, margins, money, identity, or evidence without permission. Controlled actions record requester and reject self-approval. `Session(id, user_id, expires_at, mfa_satisfied_at?, revoked_at?, version)` supports audited sign-in/out and Owner/Admin revoke; credentials/MFA secrets are never stored in business/audit payloads.

## Project and contracts

`Project(id, reference, customer_id, primary_sales_contract_id, lifecycle_state DRAFT|ACTIVE|CANCELLED, financial_state OPEN|FINANCIALLY_CLOSED, final_state OPEN|FINAL_CLOSED, management_currency, version)`.

`Contract(id, project_id, kind SALES|PURCHASE, reference, counterparty_id, active_version_id, state, version)` owns immutable `ContractVersion(id, contract_id, revision_no, effective_date, amendment_reason, coffee_specification_id, quantity, unit_price, currency, route, incoterm, named_place, quantity_tolerance_under/over, net_weight_tolerance_under/over, gross_weight_tolerance_under/over, payment_terms, document_terms, state DRAFT|PENDING_APPROVAL|APPROVED|REJECTED|SUPERSEDED, approval_id)`.

Constraints: Project creation and its sales-contract draft are atomic; exactly one SALES contract per Project; independent sales contract means another Project; >=1 purchase contract before supplier execution; omitted tolerances store zero; approved versions never mutate; reducing amendments cannot invalidate executed quantity without exact exception approval.

## Shipments and fixed route checklist

`SupplierShipment(id, project_id, purchase_contract_id, reference, active_dataset_id, execution_state DRAFT|CONFIRMED|IN_TRANSIT|RECEIVED|CANCELLED|REJECTED, version)` owns immutable `SupplierShipmentDataset(id, shipment_id, revision_no, dataset_version, dataset_hash, purchase_contract_id, supplier_id, coffee_specification_id, supplier_lot_reference, quantity, bag_count, bag_weight, net_weight, gross_weight, origin_country/location, load_location, discharge_location?, destination_country/location, incoterm, named_place, container_numbers[], seal_numbers[], transport_mode/carrier/reference/vessel_or_vehicle?/voyage_or_trip?/estimated_departure?/estimated_arrival?, planned_shipment_at?, notes?, state DRAFT|PENDING_APPROVAL|APPROVED|SUPERSEDED, approval_id?, created_by/at, revision_reason, invalidated_approval_ids[])`. The supplier schema is separate from the sales schema; no free-form `logistics` map exists.

`SalesShipment(id, project_id, sales_contract_id, reference, primary_supplier_shipment_id, active_dataset_id, execution_state DRAFT|CONFIRMED|IN_TRANSIT|DELIVERED|CANCELLED|REJECTED, financial_state OPEN|FINANCIALLY_CLOSED, document_state MISSING|DRAFT|PENDING_APPROVAL|COMPLETE, claim_state CLEAR|OPEN|UNDER_REVIEW|RESOLVED|REJECTED, version)` owns immutable `SalesShipmentDataset(id, shipment_id, revision_no, dataset_version, dataset_hash, sales_contract_id, coffee_specification_id, product_description, customer_purchase_order_reference?, marks_and_numbers?, quantity, bag_count, bag_weight, net_weight, gross_weight, origin_country/location, load_location, discharge_location, destination_country/location, incoterm, named_place, container_numbers[], seal_numbers[], transport_mode/carrier/reference/vessel_or_vehicle?/voyage_or_trip?/estimated_departure?/estimated_arrival?, planned_shipment_at?, notes?, state, approval_id?, created_by/at, revision_reason, invalidated_approval_ids[])`. These are the exact facts used by confirmation, documents, route controls, approval binding, and read workspaces.

Both workspace reads return the aggregate `reference` and linkage plus the active typed dataset, independent execution/financial/document/claim axes where applicable, current aggregate version, quantity summary, applicable approvals and graph-valid actions. `reference` is never a dataset field. Every active/history dataset read requires its owning `shipment_id` and `invalidated_approval_ids[]`. Dataset-history reads return every immutable revision in ascending `revision_no`, with dataset version/hash, change reason, actor/time, approval links, and explicit approval invalidation. Revision commands accept only dataset facts plus `changeReason` and optional `evidenceId`; they cannot accept or change shipment reference, Project/contract IDs, shipment ID, primary source, or other aggregate/linkage identity. History rows are never edited or removed.

`ShipmentExecutionEvent(id, shipment_type, shipment_id, from_state, to_state, dataset_id, occurred_at, reason, evidence_id?, actor_id, aggregate_version, idempotency_key)` is append-only. Dataset revision is allowed only in `DRAFT|CONFIRMED`; it supersedes the old active dataset, expires its approval/tolerance exception, resets `CONFIRMED` to `DRAFT`, and requires reapproval. Revision is forbidden in `IN_TRANSIT` or any terminal state. `CANCELLED|REJECTED` quantities remain visible and are excluded from active delivered/remaining calculations according to the documented formulas; no row is deleted.

Exactly one `primary_supplier_shipment_id` is required to confirm; that supplier shipment must be confirmed, in the same Project, and have compatible purchase-contract/coffee facts. There is no source-allocation entity in Release 1. Every sales confirmation requires an approved `SALES_SHIPMENT_CONFIRMATION` for the exact dataset/source binding; outside-tolerance confirmation additionally requires an approved `TOLERANCE_EXCEPTION` for the exact dataset and breached values.

`RouteChecklist(id, sales_shipment_id unique, template_code FOREIGN_TO_FOREIGN|UAE_FREE_ZONE_REEXPORT|UAE_IMPORT, template_version, snapshot_hash, status, version)` owns fixed `RouteChecklistItem(id, checklist_id, code, category EVIDENCE|MILESTONE, required, closure_blocking, state NOT_STARTED|IN_PROGRESS|SATISFIED|NOT_APPLICABLE|EXCEPTION_APPROVED, evidence_id?, milestone_at?, completed_by/at?, exception_approval_id?)`. Only template rules can mark not applicable. The snapshot cannot be redesigned by users.

## Evidence and controlled documents

`EvidenceObject(id, sha256, byte_length, media_type, object_key, object_version_id, original_filename, verification_state PENDING|VERIFIED|REJECTED, verified_by/at?, uploaded_by/at, retention_until)` is immutable. Typed API metadata always returns SHA-256, byte size, media type, verification state plus explicit verification time/actor fields, upload actor/time, immutable=true, and every source link. `PENDING` returns JSON null for both verification fields; `VERIFIED` requires both fields non-null (enforced by the OpenAPI 3.1 conditional). `EvidenceLink(id, evidence_id, subject_type, subject_id, purpose)` links an occurrence. Authorized view/download emits audit events.

`CommercialDocument(id, project_id, sales_shipment_id, kind CINV|PACKING_LIST, reference, active_revision_id, version)` owns `DocumentRevision(id, document_id, revision_no, source_sales_shipment_dataset_id, language AR|EN|BILINGUAL, generation_state QUEUED|RENDERING|READY|FAILED, lifecycle_state DRAFT|PENDING_APPROVAL|APPROVED|SENT|CANCELLED|SUPERSEDED, evidence_id?, sha256?, reason?, approval_id?, version)`.

`OutboundManifest(id, supersedes_manifest_id?, document_revision_id, document_revision_version, output_sha256, channel EMAIL, ordered_to_recipients, ordered_cc_recipients, attachment_manifest, subject, body_media_type, body_bytes_object_key, body_byte_length, body_sha256, manifest_hash, state DRAFT|PENDING_APPROVAL|APPROVED|SENT|CANCELLED|SUPERSEDED, approval_id?, version)` freezes every controlled field. Each attachment entry contains immutable evidence/document ID, revision/version, exact outbound filename, byte length, and SHA-256. Body bytes are immutable evidence-addressed content, not text regenerated at send time. Approval matches manifest version/hash; any change creates a superseding manifest and expires applicability of prior approval. Read models preserve two immutable full snapshots: approved and transport-captured sent. Each repeats the exact channel, output ID/version/hash, ordered recipients, complete attachment entries, subject, and stored body bytes/type/length/hash; acceptance compares every field and byte, not summary hashes alone.

`OutboundSendAttempt(id, manifest_id, manifest_version, manifest_hash, approval_id, attempt_no, requested_by/at, completed_at?, result ACCEPTED|DELIVERED|FAILED|UNKNOWN, provider_reference?, failure_code?, correlation_id)` is append-only. Send locks and verifies the approved stored output/body/attachments, lengths/hashes, recipients, subject, channel, and approval; mismatch or unavailable bytes fails closed and still records audit/attempt evidence. No request may supply replacement body or attachment bytes at send time.

## Supplier invoice, money, expense, and statements

`SupplierInvoice(id, project_id, supplier_shipment_id, supplier_id, reference, invoice_date, amount, currency, evidence_id, state DRAFT|PENDING_APPROVAL|CONFIRMED|REJECTED|CANCELLED, approval_id?, cancellation_reason?, version)`. A confirmed invoice is immutable; Owner/Admin may cancel only when its outstanding equals its full amount and no active allocation exists. Otherwise allocations must first be reversed. Cancellation is audited and recomputes supplier obligations/closure.

`MoneyMovement(id, project_id, party_id, contract_id, kind CUSTOMER_ADVANCE|CUSTOMER_RECEIPT|CUSTOMER_REFUND|SUPPLIER_ADVANCE|SUPPLIER_PAYMENT|SUPPLIER_REFUND|REVERSAL, direction, amount, currency, occurred_on, reference, evidence_id?, state DRAFT|CONFIRMED|PARTIALLY_ALLOCATED|FULLY_ALLOCATED|REVERSED, aed_amount?, fx_rate/date/source?, reversal_of_id?, version)`.

`SettlementAllocation(id, movement_id, target_type CINV|SUPPLIER_INVOICE, target_id, amount, currency, state ACTIVE|REVERSED, allocated_by/at, reversal_of_id?, reversal_reason?, version)`. Active totals cannot exceed movement availability or target outstanding; party and currency must match. Reversal appends a compensating row linked by `reversal_of_id`; original rows never change except derived projection state. A serializable transaction recalculates movement availability, target outstanding, all statement projections, shipment financial state, Project financial state, and final-close invalidation. Duplicate reversal is prevented by idempotency and one-active-reversal constraint.

`DirectExpense(id, project_id, sales_shipment_id?, vendor_id, category_code, amount, currency, occurred_on, evidence_id, state DRAFT|PENDING_APPROVAL|APPROVED|REJECTED|CANCELLED, approval_id?, replaces_expense_id?, replaced_by_expense_id?, cancellation_reason?, version)`. Approved fields and proof are immutable. `ExpenseCorrection(id, original_expense_id, replacement_expense_id, reason, subject_hash, approval_id, applied_at?, version)` binds the exact old/new pair; apply atomically cancels the original and approves the replacement, preserves both evidence objects, and recomputes statements/margin/closure. XOR constraint: scope is whole Project (`sales_shipment_id` null) or exactly one shipment. There is no allocation entity.

Statements are read models from confirmed movements, active settlement allocations, confirmed invoices, and approved expenses: `StatementLine(source_type/id, party/project/shipment keys, date, reference, debit, credit, currency, running_balance)`. Views exist for customer, supplier, sales shipment, supplier shipment, and Project; currencies partition balances.

## Claims, approval, profit, and closure

`Claim(id, project_id, sales_shipment_id?, supplier_shipment_id?, type QUANTITY|WEIGHT|QUALITY|DELIVERY|PRICE|DOCUMENT, claimant_id, respondent_id, description, quantity?, amount?, currency?, state OPEN|UNDER_REVIEW|RESOLVED|REJECTED, evidence_id?, version)` owns immutable `ClaimOutcomeProposal(id, claim_id, claim_version, proposed_outcome RESOLVED|REJECTED, reason, evidence_id?, subject_hash, state PENDING_APPROVAL|APPROVED|REJECTED|EXPIRED|APPLIED, approval_id?, applied_at?)`. Submission leaves claim `UNDER_REVIEW`; only application of an approved exact proposal changes terminal claim state. No automated settlement rows are created.

`Approval(id, action_code, subject_type/id, subject_version, subject_hash, requester_id, decision PENDING|APPROVED|REJECTED|EXPIRED, approver_id?, decided_at?, reason/comment?, evidence_id?)` is immutable after decision. Fixed action codes are exactly those in the spec matrix. Approver differs from requester. A later subject version/hash expires applicability. The fixed inbox projection is `ApprovalInboxItem(approval_id, action_code, exact subject_type/id/reference/version/hash, changed_fields old/new, evidence metadata/source links, detected_conflicts, requester snapshot/requested_at, required_role, decision_context, approval_state/version)` so its decision dialog never has to infer or refetch controlled facts.

`ProfitSnapshot(id, project_id, project_version, as_of, currency, expected_margin, committed_margin, actual_operational_margin, cash_position, formula_version, input_hash, generated_at)` owns drill-down `ProfitLine(snapshot_id, measure, source_type/id, amount, currency, explanation)`. Advances affect cash only.

`ClosureAssessment(id, project_id, project_version, assessed_at, quantity_delivery_complete, route_complete, documents_complete, supplier_obligations_complete, expenses_complete, claims_complete, approvals_complete, blockers_hash)` owns `ClosureBlocker(id, assessment_id, code, subject_type/id, message_key, exception_eligible, covered_by_approval_id?)`.

Closure blocker completeness is derived only from reachable active rows: every non-cancelled sales shipment delivered and financially closed; every non-cancelled supplier shipment received with at least one confirmed non-cancelled supplier invoice and every such invoice at zero outstanding; route items satisfied; every non-cancelled sales shipment has approved non-cancelled CINV/Packing List and its CINV customer outstanding is zero; expenses approved or validly cancelled/replaced; claims terminal through applied approved proposals; and required approvals current. Balance, immutable/audit, approval-integrity, and security blockers are never exception-eligible.

Financial states are computed: shipment closes iff at least one approved, non-cancelled CINV exists and its aggregate customer outstanding is exactly zero; Project closes financially iff all non-cancelled shipments do. `FINAL_CLOSED` requires a current assessment and every blocker absent or covered by an eligible exact blocker/version exception. Reopen records reason and recomputes financial state. Any reversal/refund, shipment cancellation/rejection, document cancellation/revision, expense correction, or new/reopened claim invalidates affected assessments/exceptions and sets final state `OPEN` atomically; financial state independently follows exact customer outstanding balances.

## Recovery evidence

`BackupSnapshot(id, database_backup_id, object_snapshot_id, completed_at, encrypted, separate_copy, rpo_minutes, manifest_hash)` and `RestoreTest(id, backup_snapshot_id, isolated_environment, requested_by/at, state QUEUED|RUNNING|PASSED|FAILED, completed_at?, rpo_minutes?, rto_minutes?, evidence_id?, version)` expose status/evidence without exposing backup credentials. A PASS requires restored row/version/hash/allocation/approval/audit/object-link checks; tests never overwrite production.

## Audit and request integrity

`AuditEvent(id, project_id, aggregate_type/id, aggregate_version, sequence_no, action, actor_id plus immutable display-name/role snapshot, session_id, occurred_at, reason?, correlation_id, idempotency_key?, before_hash?, after_hash, previous_event_hash, event_hash)` is append-only and transactionally written. The hash payload contains exactly these keys (excluding `event_hash`): `id, projectId, sequenceNo, actor, sessionId, action, aggregateType, aggregateId, aggregateVersion, beforeHash, afterHash, previousEventHash, occurredAt, reason, correlationId, idempotencyKey`. Every key is present; unavailable optional values are JSON `null`; no extra key is hashed. `eventHash = lowercase-hex(SHA-256(UTF-8(RFC8785-JCS(hashPayload))))`. Genesis `previousEventHash` is JSON `null`; every later value is the immediately preceding Project event hash. Project audit pages are strictly ascending and return required start/end continuity anchors, including across cursors, so independent clients can recompute every event. Daily signed heads are retained in object storage.

`PilotSession(id, user_id, created_at, last_seen_at, idle_expires_at, absolute_expires_at, revoked_at?, revoked_by?, revocation_reason?, current, version)` is listable by Owner/Admin and revocable by exact user/session ID. Every listed session returns all three revocation fields: they are JSON null while active and required non-null when `revoked=true`; the revoke response is subject to the same OpenAPI 3.1 conditional. Every authenticated fixed role may revoke its own current session through sign-out; cross-user/session revocation remains Owner/Admin only. The `__Host-orb_session` cookie is Secure, HttpOnly, SameSite=Strict, Path=/ and has no Domain; every cookie-authenticated mutation requires a session-bound CSRF header plus allow-listed Origin/Referer validation that fails closed. Session/CSRF rotation occurs at sign-in, reauthentication, and privilege change; idle expiry is 30 minutes and absolute expiry is 12 hours.

`IdempotencyRecord(actor_id, operation_id, key, request_hash, response_status, response_locator/hash, created_at, expires_at)` is unique by actor/operation/key; same key/different request fails. Existing-aggregate commands require quoted version via `If-Match`.

## Explicitly absent from Release 1 schema

No bank statement/import/match, tax pack/classification, migration staging, supplier-source allocation, expense allocation, configurable approval policy/designer, dynamic route template designer, or advanced claim settlement entity exists. No closure rule references them.
